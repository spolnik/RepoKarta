Maps answer two different questions. A **repository map** describes static
structure inside a codebase. **System topology** assembles deployable
components and directed communication across repositories. Keeping those
models separate prevents an import from becoming an invented service call. The
demonstration below moves through the structural lenses and finishes on the
HTTP route evidence.

## Repository-map lenses

<CardGrid>
	<Card title="System" icon="seti">Packages, entry points, routes, dependencies, and strongest edges.</Card>
	<Card title="Packages" icon="puzzle">Source organization and high-signal package relationships.</Card>
	<Card title="Dependencies" icon="link">Declared packages and dependency facts, not runtime ownership.</Card>
	<Card title="Routes" icon="globe">Served endpoints connected to their controller or handler source.</Card>
</CardGrid>

Each map can be searched, filtered, switched to exact list view, exported by a
permissioned endpoint, and queried as an evidence graph. **Focus neighbors**
creates a bounded local investigation without changing the underlying snapshot.

## Fleet topology

```text
static source + manifests + deployment configuration
                         │
                         ▼
       component ── directed relationship ── component
          │             HTTP / gRPC / Kafka / DB / MCP
          └──────── evidence + resolution status ────────┘
                         ▲
                         │
             optional runtime observations
```

Topology first composes fleet evidence, then applies repository scope. That
ordering preserves inbound callers from repositories outside the selected
component’s codebase.

| Relationship state | Meaning |
| --- | --- |
| resolved static | source/configuration identifies a component target |
| runtime observed | imported observation corroborates or adds an environment/provider edge |
| unresolved | a call exists but ownership cannot be safely assigned |
| suppressed | deployment-only or invalid source evidence was deliberately excluded |
| rejected component | candidate failed component validation and is reported diagnostically |

Topology supports component-level HTTP, gRPC, Kafka, database, and MCP
relationships; filters include repository, protocol, origin, provider,
environment, `static_only`, direction, and bounded neighborhood depth.

## Read topology without inventing ownership

<Steps>
1. Begin with one component and both inbound and outbound directions.
2. Set depth to one for direct relationships; expand to two only when the first
   neighborhood suggests a transitive path.
3. Inspect relationship protocol, origin, environment, resolution tier, and
   every evidence citation.
4. Keep unresolved targets unresolved until configuration or runtime evidence
   identifies their owner.
5. Use repository maps to explain internal structure and topology to explain
   deployed communication; do not merge the claims.
</Steps>

<Aside type="note" title="Runtime evidence supplements static evidence">
	Observation import records provider and environment and can corroborate a
	static relationship. It does not erase the original source/configuration
	evidence or silently convert uncertainty into certainty.
</Aside>
