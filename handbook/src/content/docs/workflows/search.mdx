## Four query engines, one result contract

| Mode | Use it for | Precision boundary |
| --- | --- | --- |
| Zoekt syntax | fast default search, boolean terms, paths, languages | committed text |
| Literal | punctuation-heavy strings, URLs, error messages | exact text |
| Regular expression | families of names or structured strings | regex over indexed text |
| SCIP / AST references | definitions, references, implementations | SCIP when ready; labelled syntax fallback |

Typed `result_type` queries extend the same box to `symbol_definition`,
`symbol_implementation`, `reference`, `route`, `commit`, `diff`, map entities,
and generated documents.

```text
OwnerResource repository:spring-petclinic-microservices
"/api/search" result_type:route repository:RepoKarta
"connection refused" language:Go -path:vendor
author:"Alex Smith" result_type:commit after:2026-01-01
```

## Progressive refinement

<Steps>
1. Start with the name, route, error, or concept you remember.
2. Read the repository, language, and path facets returned by the actual result
   set.
3. Add one constraint: repository, language, path, file, or result type.
4. Raise the result limit only when the response reports truncation; a narrower
   query is usually more useful.
5. Open source, history, map, or Wiki from the result rather than starting a
   second disconnected investigation.
</Steps>

## Contexts: reusable repository scope

A context is a permission-checked set of repositories and current indexed
revisions. RepoKarta resolves explicit repositories, named contexts, and
defaults into one effective scope with provenance and a canonical URL.

<CardGrid>
	<Card title="Explicit" icon="document">
		A one-off repository selection in Search, Chat, or MCP.
	</Card>
	<Card title="Personal" icon="person">
		A reusable context owned by one identity.
	</Card>
	<Card title="Published" icon="globe">
		An administrator-managed context available to permitted users.
	</Card>
	<Card title="Default" icon="star">
		The context automatically applied when the caller does not specify one.
	</Card>
</CardGrid>

Changing repository access changes effective context resolution; a stored
context does not grant access by itself.

## Saved searches and monitors

The Search workspace keeps recent deterministic queries in the browser and can
persist named searches. A monitor attaches a schedule and records explicit
runs so a query can become a repeatable check.

<Tabs>
	<TabItem label="Save">
		Name the current query after its intent—“new public admin routes” is more
		useful than “route search”. The saved record keeps the query and scope.
	</TabItem>
	<TabItem label="Monitor">
		Enable the monitor on a saved search, choose its cadence, and use **Run
		now** to establish the first observed result before relying on schedule.
	</TabItem>
	<TabItem label="Review">
		Compare the monitor’s recorded runs with the indexed revisions. A changed
		result and a newly indexed commit are separate pieces of evidence.
	</TabItem>
</Tabs>

<Aside type="caution" title="Partial does not mean absent">
	Truncation, skipped candidate files, skipped shards, a building structural
	artifact, or a lower-precision reference provider all limit the negative
	conclusions you can draw. RepoKarta returns those limits in the result.
</Aside>
